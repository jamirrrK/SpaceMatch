# Deployment plan — execution locked

This is a plan for a separately approved release, not authorization to connect to hosting or deploy. No production environment has been inspected in this development stage.

1. Finish the user's additional requirements, obtain approval of the local browser demonstration, then identify the exact reviewed Git commit. Do not push or merge without separate permission. Use the existing protected production environment and explicit approval gates; do not enable them as part of local development.
2. Build in a clean checkout with the locked dependencies: Composer on the build machine, `npm ci`, `npm run build`, full Laravel tests and offline deployment tests. Hosting must receive the compiled Vite manifest, CSS, JavaScript, font and optimized static images; Node/npm is not required there. Relative compiled font references support subdirectory document roots. Verify the actual domain, document root and configured asset URL before release.
3. Verify PHP 8.3 and required extensions against the actual application's Composer platform requirements. Existing private production dependencies may be reused only with the hardening scripts' verified compatibility receipt and matching Composer lock/inventory. A missing receipt, changed lock, incompatible platform or unverified provisioning method blocks deployment. Do not assume Composer exists on hosting and do not overwrite private vendor dependencies.
4. Verify all tools required by the selected transfer/recovery method. The automated path requires the tools checked by `deploy.sh`; Z.com cPanel may lack SSH, Bash/Python support or rsync. If requirements are absent, that automated path stays blocked until an independently reviewed, recoverable cPanel-compatible method exists. Do not substitute an unreviewed FTP copy or assume VPS privileges.
5. Verify exact Laravel/private/public paths, private storage separation, writable runtime/cache directories, persistent uploads and `.env` preservation. Review the managed deletion allowlist against the actual server tree. No deletion may include uploads, runtime storage, credentials or private dependencies.
6. Verify release identity and complete artifact/file/asset manifests. Run read-only preflight, test baseline application health, confirm no incomplete prior transaction, and require recent intact file/database backups with the correct commit association. Backups must have a documented restore owner and procedure.
7. Inspect production migration history and compare it to the approved release without running migrations during this development phase. This stage adds no migrations. Existing pending or incompatible migrations block the current automated deployment path. SQLite test results do not establish MySQL/MariaDB production compatibility; test any future schema changes in a separate matching database first.
8. During a separately authorized deployment, retain the last working code release and protect current user activity. Use the approved maintenance, copy, cache and application-health checks. A failed new release may restore the preserved code only when compatible with current data. Never automatically restore a database snapshot over newer activity.
9. Confirm application health, maintenance-mode exit, real asset/image delivery, login/OTP, role access and representative read-only workflow pages. Record the release commit and outcome. If safe restoration cannot be confirmed, keep maintenance mode where possible and require operator intervention; if maintenance cannot be confirmed, the existing recovery procedure requires disabling public access through cPanel. Preserve transaction history and backups for diagnosis.

Actual hosting capabilities, dependency receipts, backups, production state and release parity remain unverified. Consult the existing deployment-hardening runbook and scripts for executable checks; do not bypass their blockers.

## Remaining limitations

1. Actual Z.com account capabilities cannot be verified under this phase's prohibition on production connection. Shell/Terminal access itself is provider-controlled; Python 3.10/fcntl/TLS, quota, PHP binary/extensions, web ownership, writable paths and egress remain unknown. If any requirement is unavailable, keep deployment blocked and design a separately reviewed provider-compatible alternative. SFTP alone is insufficient.
2. No verified dependency provisioning method/bundle or receipt is available yet. The controller deliberately cannot bless unknown existing vendor contents and cannot install dependencies. Matching hashes prove equality to a reviewed baseline, not independent provenance or semantic code compatibility. New dependency requirements, classmap/namespace moves and Composer-file changes need separate review/provisioning.
3. Dependency, backup and hosting records are private operator trust records, not cryptographic attestations. They must be created from actual review/restore evidence, never by changing placeholders or hashing an unverified live directory and calling it approved. Installed vendor is hashed completely; this may take time/IO on shared hosting.
4. Live schema drift requires a separate schema review. Equal migration files and applied names do not prove table/index/foreign-key equivalence. The user-reported migration state and OTP delivery were not reverified.
5. Split-directory updates are not atomic. Writers, cron and queues must remain paused through health and functional review. Reopening for HTTP checks can admit activity; code recovery never rolls back that activity. Full writer quiescence needs an approved hosting/application procedure.
6. Automatic recovery handles catchable errors/SIGINT/SIGTERM, not SIGKILL, power loss or filesystem failure. Unresolved history blocks subsequent CLI deployments, but an interruption after reopening can leave health unconfirmed. Independent cPanel/provider access is needed to restrict web service when the guard cannot be confirmed. No guarantee is made that a broken custom entrypoint reads the guard; that is a hard readiness prerequisite.
7. Health checks do not exercise authenticated/OTP/business workflows or external email services. OPcache and persistent workers require verified hosting behavior; unsupported process-management arrangements block deployment.
8. GitHub environment settings/plan support and immutable action commit pins remain unverified. Actions currently use major tags; pin and independently review them before any production enablement. YAML validation is not evidence of a successful GitHub runner build.
9. Archive digests and manifests detect corruption, not authenticity without a trusted approved workflow/run/digest. Exact source inventory is validated at packaging; an independently malicious manifest can lie about its own source list. Review source and archive provenance.
10. Full runtime/database backup creation and restore testing are operator procedures; checksum/tar/gzip checks are not proof of semantic restoration. No automatic retention cleanup, production credential setup, remote transport or live migration workflow is implemented.
11. Native permissions/flock/symlink behavior and actual PHP/HTTP integration still need isolated Linux and cPanel-equivalent rehearsal. The production CLI deliberately has no override that points it at arbitrary application roots. Build a reviewed staging harness around the controller for a separate staging app/database; never test the production CLI against the live paths merely to satisfy this prerequisite.
12. Source/static directory classification is reviewed manually. If uploads currently live under public/assets or public/vendor, relocate them through a separately approved plan or redesign the managed inventory before approving deployment. Do not label them managed just to pass preflight.
